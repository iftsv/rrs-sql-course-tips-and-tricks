## 🛒 2. Концепция RDBMS: Аналогия с чеком из Costco
Лучший способ закрепить понимание реляционных баз данных — разложить физический чек из магазина Costco по таблицам. База данных спроектирована так, чтобы минимизировать дублирование данных и связать сущности между собой [4, 5].

### Как разложить чек по таблицам:
1. **Таблица `Store` (Магазины):**
   * *Данные из чека:* Адрес "Эль Камино" и локация №475 [4, 5].
   * *Поля:* ID локации, адрес, телефон конкретного филиала [5].
2. **Таблица `Customer` (Клиенты):**
   * *Данные из чека:* Номер членской карты (Member ID: 11842...) [5].
   * *Поля:* Уникальный ID клиента, имя, тип подписки, статус [5].
3. **Таблица `Product` (Товары):**
   * *Данные из чека:* Sweet Potato, Medalin cookies, Mushrooms [5].
   * *Поля:* ID товара, наименование, цена [5].
4. **Таблица `Transaction` (Транзакции / Чеки):**
   * *Данные из чека:* Дата и время (25 сентября), номер транзакции №475, ID кассира (Омарзи №107) [5].
   * *Поля:* ID транзакции, дата, ID магазина, ID клиента, ID кассира [5].

### 💡 QA-Кейс: Зачем это тестировщику?
* **Интеграционное тестирование (Фронтенд -> Бэкенд):** Когда пользователь на сайте нажимает кнопку «Оплатить», фронтенд отправляет запрос на бэкенд. Задача QA — проверить, что в БД создалась запись в таблице `Transaction`, при этом она правильно связалась с ID существующего клиента (`customer_id`) и ID купленного товара (`product_id`). Если связь запишется неверно, клиент получит чужой заказ, а аналитики увидят некорректную аналитику продаж.

## 🔑 3. Ключи в БД: Primary Key vs Foreign Key
Связи в реляционных базах данных строятся за счет ключей. В MySQL Workbench они имеют четкие графические обозначения [27].

### Primary Key (Первичный ключ)
* **Что это:** Уникальный идентификатор строки в таблице (например, `customer_id` или `product_id`) [7, 8]. Он никогда не повторяется в рамках одной таблицы и не может быть пустым (NOT NULL) [7, 8].
* **Обозначение в Workbench:** **Желтая лампочка (или золотой ключик)** [27]. Всегда идет первой колонкой в таблице [8].

### Foreign Key (Внешний ключ)
* **Что это:** Поле-коннектор, которое ссылается на Primary Key в другой таблице [8]. Например, в таблице транзакций (`Transaction`) поле `customer_id` является внешним ключом, ссылающимся на первичный ключ таблицы `Customer` [8].
* **Обозначение в Workbench:** **Красный ромбик** [27].
* **Важное отличие:** Внешние ключи могут дублироваться (один и тот же клиент может совершить много покупок, поэтому его `customer_id` будет многократно повторяться в таблице транзакций) [8].

### 💡 QA-Кейс: Зачем это тестировщику?
* **Негативное тестирование ссылочной целостности (Referential Integrity):** QA должен проверить поведение системы при попытке нарушить связи. Например, если попробовать через API удалить профиль клиента (`customer_id = 99`), у которого в базе уже есть совершенные покупки (записи в `Transaction`), база данных должна заблокировать это удаление благодаря ограничению Foreign Key Constraint. Тестировщик проверяет, что сервер не падает с ошибкой 500 Internal Server Error, а возвращает валидную ошибку пользователю, предотвращая появление в системе "сиротских" записей транзакций без привязанного клиента.

## 📂 4. Три языка внутри SQL: DDL, DQL, DML
SQL (Structured Query Language) — это семейство из трех основных языков, каждый из которых решает свои задачи [10, 11].

| Компонент SQL | Расшифровка | С чем работает | Ключевые команды | QA-Юзкейс |
| :--- | :--- | :--- | :--- | :--- |
| **DDL** [10] | Data Definition Language (Язык определения данных) | **Структура** таблиц и баз данных (схемы) [10] | `CREATE`, `ALTER`, `DROP` [10] | Используется автотестами при инициализации базы (создание временных таблиц для прогона тестов). |
| **DQL** [10, 11] | Data Query Language (Язык запросов данных) | **Выборка** и просмотр колонок [10, 11] | `SELECT` [10, 11] | Главный инструмент QA для ручной и автоматической верификации данных после шагов тест-кейса. |
| **DML** [11] | Data Manipulation Language (Язык манипулирования данными) | **Записи** (строки с данными) внутри таблиц [11] | `INSERT`, `UPDATE`, `DELETE` [11] | **Data Seeding (Подготовка тестовых данных)**. Быстрое создание нужного состояния пользователя прямо в БД. |

### 💡 QA-Кейс для DML (Тестовые данные):
Вместо того чтобы вручную проходить длинный UI-сценарий регистрации нового пользователя, подтверждения его почты, накопления бонусных баллов и получения VIP-статуса, QA-инженер выполняет один быстрый DML-запрос перед тестом:
```sql
UPDATE users 
SET status = 'VIP', email_verified = true, bonus_balance = 5000 
WHERE id = 123;
```
Это экономит часы времени при тестировании сложных фич.

## 🛠️ 5. Практическая настройка MySQL Workbench

Для того чтобы студенты могли полноценно выполнять домашние задания и писать запросы, им необходимо сделать несколько базовых настроек [27].

### 1. Отключение безопасного режима (Safe Updates)
По умолчанию MySQL Workbench блокирует операции изменения (`UPDATE`) и удаления (`DELETE`) данных, если в запросе в блоке `WHERE` не указан первичный ключ [18]. Это сделано для безопасности продакшена, но мешает при подготовке тестовых данных [18].
* **Инструкция для студентов:**
  1. Перейдите в меню: `Edit` -> `Preferences` [18].
  2. Выберите вкладку: `SQL Editor` [18].
  3. Проскролльте в самый низ и **снимите галочку** с чекбокса `Safe Updates (rejects UPDATEs and DELETEs with no restrictions)` [18].
  4. **Обязательно перезапустите соединение** (Reconnect to Database / Перезапустить Workbench) [18].

### 2. Оформление кода и комментарии в SQL
Важно приучать студентов писать аккуратный, читаемый код. Комментарии помогают документировать шаги тест-кейсов [25].
* **Однострочный комментарий:** Начинается с двух дефисов и пробела `-- ` [25].
* **Многострочный комментарий:** Заключается в конструкцию `/* текст комментария */` [25].

```sql
-- Это однострочный комментарий: проверка списка клиентов
SELECT * FROM classicmodels.customers; 

/* 
Это многострочный комментарий.
Используется для подробного описания тест-кейса:
Шаг 1: Проверить статус заказа у клиента №124
*/
```

### 3. Инструмент EER-диаграммы (Enhanced Entity Relationship)
Это интерактивная дорожная карта базы данных, которая показывает, как именно таблицы связаны через PK и FK [25, 27].
* **Как сгенерировать в Workbench:**
  1. Выбрать в верхнем меню `Database` -> `Reverse Engineer...` [26]
  2. Нажать `Next`, ввести пароль от вашей локальной БД [26].
  3. Выбрать схему `classicmodels`, нажать `Next` и дождаться завершения (`Execute`) [26].
* **Польза для QA:** Позволяет визуально оценить архитектуру системы перед составлением плана интеграционного тестирования.

## 🔍 6. Разбор типичной ошибки студентов (Кейс на ревью!)
При повторном запуске скрипта развертывания базы данных `Classic Models` многие студенты столкнулись с ошибкой в логах:
`Error Code: 1217. Cannot drop table productlines referenced by foreign key` [31, 34].

### Почему возникает ошибка?
В начале скрипта прописаны команды удаления существующих таблиц, чтобы создать их заново (например, `DROP TABLE IF EXISTS productlines;`). Однако таблица `productlines` является родительской. На её первичный ключ ссылаются внешние ключи из таблицы `products` [31]. СУБД MySQL блокирует удаление (DROP) родительской таблицы для защиты целостности данных, так как иначе дочерняя таблица останется со ссылками на несуществующие строки [34].

### Как объяснить студентам на ревью:
1. **Данные на месте:** Эта ошибка возникает **только при повторном запуске** скрипта, когда база данных уже успешно создана в первый раз [37]. Так как все таблицы уже развернуты и наполнены данными, повторно запускать этот тяжелый скрипт настройки не нужно [37]. Все готово к работе! [37]
2. **Как это обходят разработчики / автоматизаторы:** Чтобы принудительно пересоздать базу данных со всеми связями, перед удалением таблиц временно отключают проверку внешних ключей, а затем включают ее обратно:
   ```sql
   SET FOREIGN_KEY_CHECKS = 0; -- Отключаем проверки
   DROP TABLE IF EXISTS productlines;
   DROP TABLE IF EXISTS products;
   -- ... создание таблиц заново ...
   SET FOREIGN_KEY_CHECKS = 1; -- Включаем проверки обратно
   ```

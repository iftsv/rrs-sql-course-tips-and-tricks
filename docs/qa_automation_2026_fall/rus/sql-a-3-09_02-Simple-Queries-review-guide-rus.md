### 🕵️‍♂️ 2. Концепция сессии: База данных как «Черный ящик» (Black Box)
Если на первом занятии мы разбирали структуру базы на примере понятного чека из магазина [13], то на втором занятии ключевой фокус смещается на **исследование незнакомой системы**. 

В реальной работе QA-инженеру часто приходится сталкиваться с ситуациями «черного ящика»:
*   Документация к базе данных отсутствует или устарела.
*   Доступа к визуальным инструментам генерации схем (ER-диаграмм) в рабочей среде нет [46, 55].
*   Есть только терминал или консоль для выполнения SQL-запросов.

Умение писать простые запросы выборки (DQL) и работать с системными таблицами — это «фонарик» тестировщика, который позволяет быстро сориентироваться в незнакомой базе, понять ее структуру и начать эффективно тестировать бэкенд с первого дня на проекте [46].

### 🔢 3. Подсчет записей и лимиты: Почему это важно для QA

#### Три способа посчитать записи в MySQL Workbench [3, 43]:
1.  **Запрос `SELECT COUNT(*)` (Самый надежный способ)** [3, 43]:
    ```sql
    SELECT COUNT(*) FROM classicmodels.customers;
    ```
    *   **Почему это суперсила QA:** Позволяет мгновенно получить точное число без ручного пролистывания [43]. В отличие от UI-инструментов, этот запрос возвращает одну цифру, которую легко использовать в автотестах для верификации.
    *   **💡 QA-Кейс (Миграция и Интеграция):** При тестировании переноса данных (Data Migration) из старой CRM в новую базу данных, QA должен выполнить сверку объемов. Если в исходной системе было 122 клиента, то `SELECT COUNT(*)` в целевой базе должен выдать ровно 122 [2, 3]. Разница даже в одну запись сигнализирует о потере данных при миграции.

2.  **Анализ Action Output (Окно логов)** [29, 30]:
    *   При запуске обычного `SELECT * FROM table;` в нижней панели Workbench (Action Output) отображается количество возвращенных строк (например, *122 rows returned*) [29].
    *   *Подвох для QA:* Если в Workbench выставлен принудительный лимит в настройках (например, Limit to 1000), а в таблице миллион записей, лог покажет только лимит, что может ввести в заблуждение [42].

3.  **Иконка информации (Hover over "i" icon)** [3, 66]:
    *   В боковой панели схем (Schemas) при наведении на таблицу можно нажать на иконку «i» и увидеть метаданные, включая число строк (`Table rows`) [3, 66].
    *   *Подвох для QA:* Это значение кэшируется СУБД (особенно в InnoDB) и часто является приблизительным. Для точных проверок всегда используем `COUNT(*)` [3].

#### Ограничение вывода данных (LIMIT) [2, 38]:
Разные СУБД используют разный синтаксис для ограничения строк [2, 38]:
*   **MySQL:** `LIMIT 10;` [2, 38]
*   **SQL Server:** `TOP 10` [2, 38]
*   **Oracle:** `WHERE rownum = 10` или `FETCH FIRST 10 ROWS ONLY` [2, 38]

*   **💡 QA-Кейс (Пейджинация и Производительность):** 
    При тестировании веб-страницы с пагинацией (например, отображение списка товаров по 10 штук на странице), QA-инженер должен убедиться, что бэкенд не вытягивает всю базу данных за раз. Запрос с `LIMIT 10` (и `OFFSET` на реальных проектах) обеспечивает быструю загрузку страницы. Тестируя API, мы проверяем, что бэкенд отправляет в БД именно оптимизированный запрос с лимитом, чтобы избежать падения производительности и утечек памяти на сервере.

### 📋 4. Структура запроса: Анатомия простого оператора выборки

Строгий порядок написания и выполнения инструкций в SQL для одной таблицы [45]:
```sql
SELECT column1, column2  -- ЧТО выбираем (колонки)
FROM table_name          -- ОТКУДА выбираем (таблица)
WHERE condition          -- КАК фильтруем (условие)
ORDER BY column_name     -- КАК сортируем (порядок)
LIMIT N;                 -- СКОЛЬКО строк возвращаем (лимит) [45]
```

#### Ключевые правила синтаксиса для студентов [4, 40, 41]:
*   **Регистронезависимость:** SQL нечувствителен к регистру (`SELECT` и `select` работают одинаково), но хорошим тоном считается писать зарезервированные слова заглавными буквами для читаемости кода [40].
*   **Зарезервированные слова (Reserved Words):** Подсвечиваются синим цветом в редакторе (например, `SELECT`, `FROM`, `STATUS`) [40, 41]. 
*   **Косые кавычки (Backticks `` ` ``):** Если имя столбца или таблицы совпадает с зарезервированным словом (например, таблица или колонка называется `` `select` `` или `` `status` ``), его необходимо обернуть в косые кавычки (клавиша Ё / ~ на клавиатуре), чтобы СУБД поняла, что это идентификатор, а не команда [41, 62].
*   **Точка с запятой (Semicolon `;`):** Является разделителем запросов (командой Commit для Workbench) [40]. Она указывает СУБД, что выполнение текущей «задачи» (job) завершено и можно переходить к следующей [40].
*   **Кавычки для данных:** Текстовые значения и даты в условиях `WHERE` всегда пишутся в **одинарных кавычках** (`country = 'Norway'`), числа пишутся **без кавычек** (`creditLimit >= 50000`) [4, 59].
*   **Шорткаты сессии:** Команда `USE database_name;` позволяет задать базу по умолчанию [4, 44]. После этого можно не писать полное имя таблицы через точку (`classicmodels.customers`), а сократить до простого названия таблицы (`customers`) [4, 44].

### 🔮 5. Сверхсила QA: Работа «вслепую» (INFORMATION_SCHEMA и DESC)

Когда у тестировщика нет под рукой ER-диаграммы, он использует возможности метаданных [46, 47].

#### 1. Описание структуры таблицы через `DESCRIBE` [6, 52]:
Команда `DESC table_name;` (или сокращенно `DESCRIBE`) возвращает структуру таблицы: список полей, типы данных (VARCHAR, INT, DATE), разрешен ли NULL, ключи (PRI/MUL) и значения по умолчанию [6, 52].
```sql
DESC classicmodels.customers;
```
*   **Зачем это QA:** Помогает мгновенно понять ограничения полей (например, максимальную длину строки в VARCHAR) для составления тест-кейсов на граничные значения без обращения к разработчикам.

#### 2. Запросы к системному каталогу `INFORMATION_SCHEMA` [4, 5, 47]:
`INFORMATION_SCHEMA` — это встроенная база данных, содержащая метаданные обо всех объектах сервера СУБД [4, 47].

*   **Как увидеть все таблицы и точное количество строк в них за один быстрый запрос [5, 49]:**
    ```sql
    SELECT TABLE_NAME, TABLE_ROWS 
    FROM INFORMATION_SCHEMA.tables 
    WHERE TABLE_SCHEMA = 'classicmodels';
    ```
    *Это избавляет от необходимости писать индивидуальные `COUNT(*)` для каждой из 8+ таблиц [49].*

*   **Как получить список всех 59 колонок базы данных с типами данных [5, 49]:**
    ```sql
    SELECT TABLE_NAME, COLUMN_NAME, ORDINAL_POSITION, COLUMN_TYPE, COLUMN_KEY 
    FROM INFORMATION_SCHEMA.columns 
    WHERE TABLE_SCHEMA = 'classicmodels' 
    ORDER BY TABLE_NAME, ORDINAL_POSITION;
    ```
    *   **💡 QA-Кейс:** Имея результаты этого запроса, тестировщик может скопировать их в Excel и полностью воссоздать структуру связей БД, даже если функция Reverse Engineer заблокирована правами доступа [50, 51, 55]!

*   **Как проверить Primary и Foreign Keys (связи/ограничения) [5, 47]:**
    ```sql
    SELECT * 
    FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE 
    WHERE TABLE_SCHEMA = 'classicmodels' AND TABLE_NAME = 'customers';
    ```
    *В результатах мы увидим, что `customerNumber` является Primary Key (PRI), а связь с сотрудниками настроена через Foreign Key на колонку `salesRepEmployeeNumber` [48].*

#### ⚠️ Ловушка на собеседовании: Двойной смысл слова `DESC`
Объясните студентам, что ключевое слово `DESC` в MySQL имеет два абсолютно разных значения в зависимости от контекста:
1.  **DESC как DESCRIBE (Описание структуры):** Пишется *перед* именем таблицы. Пример: `DESC customers;` — возвращает схему таблицы (колонки, типы данных) [6, 52].
2.  **DESC как DESCENDING (Сортировка по убыванию):** Пишется *после* имени колонки в блоке сортировки. Пример: `ORDER BY score DESC;` — сортирует данные от большего к меньшему (от Z к A) [2, 39].

### 🎯 6. Практический тренажер: Разбор запросов (ClassicModels)

Ниже приведены ключевые учебные запросы второго занятия с точки зрения прикладных задач тестирования (QA-контекст) [6, 7, 8].

| SQL-запрос | Что делает | 💡 QA-контекст: Зачем это тестировщику? |
| :--- | :--- | :--- |
| `SELECT * FROM customers WHERE country = 'Norway';` [6] | Находит всех клиентов из Норвегии [6]. | **Тестирование локализации и налогов:** Проверка, что для пользователей из Норвегии правильно рассчитывается стоимость доставки и применяется соответствующий налог (НДС) на бэкенде. |
| `SELECT * FROM customers WHERE creditLimit BETWEEN 50000 AND 60000;` [6] | Выбирает клиентов с лимитом от 50 до 60 тыс [6]. | **Анализ граничных значений (BVA):** Выборка тестовых учетных записей, находящихся на границах эквивалентных классов (ровно 50к, 60к, внутри диапазона) для проверки логики предоставления скидок. |
| `SELECT * FROM employees WHERE jobTitle LIKE '%VP%';` [7] | Находит всех вице-президентов (VP) [7, 58]. | **Тестирование поиска на UI:** Проверка работы неполного текстового поиска (Partial Search). Символы `%` говорят СУБД искать любые символы до и после букв "VP" [58, 59]. |
| `SELECT city, phone FROM offices WHERE city IN ('San Francisco', 'Boston');` [7] | Выводит только город и телефон для SF и Бостона [7, 59]. | **Тестирование фильтров мультиселекта:** Когда на UI пользователь выбирает чекбоксами несколько городов в фильтре, бэкенд должен преобразовать это в оператор `IN (...)`, а не громоздкие условия `OR` [59, 60]. |
| `SELECT * FROM offices WHERE state IS NULL;` [7] | Находит офисы, у которых не указан штат [7, 60]. | **Тестирование необязательных полей:** В США поле `state` обязательно, но для международных офисов (Япония, Франция) оно должно оставаться пустым (`NULL`) [60]. QA проверяет, что система корректно обрабатывает отсутствие данных и не падает с ошибкой (NullPointerException). |
| `SELECT orderNumber, quantityOrdered FROM orderdetails ORDER BY quantityOrdered DESC;` [7] | Выводит детали заказов, отсортированные по количеству от большего к меньшему [7]. | **Тестирование сортировки UI:** Проверка корректности сортировки товаров в личном кабинете или админ-панели. QA сравнивает порядок строк на экране с порядком в БД при сортировке по убыванию [7, 61]. |
| `SELECT DISTINCT status FROM orders;` [8] | Показывает уникальные статусы заказов в системе [8, 62]. | **Проектирование тестов жизненного цикла (State Transition):** Чтобы протестировать переходы заказа из статуса в статус (In Process -> Shipped -> Resolved), QA сначала должен узнать через `DISTINCT`, какие вообще статусы заложены в базе данных [61, 62]. |

### 🔍 7. Разбор типичных ошибок и затыков студентов (Кейс на ревью!)

Во время выполнения ДЗ студенты часто сталкиваются со следующими проблемами. Разберите их превентивно [68].

#### 1. Проблема: «Я запустил скрипт создания базы данных `universitydb.sql`, лог успешный, но база не появилась слева!» [65, 68]
*   **Причина:** MySQL Workbench не обновляет дерево баз данных (Schemas) в реальном времени автоматически при создании баз через внешние скрипты [68].
*   **Как объяснить на ревью:** Показать студентам, что нужно кликнуть правой кнопкой мыши по пустому белому пространству в панели Schemas слева и выбрать **`Refresh All`** [68]. Схема `universitydb` мгновенно появится в списке [65, 68].

#### 2. Проблема: Путаница между Лимитом в UI Workbench и лимитом в SQL-запросе [38, 42]
*   **Причина:** В верхнем меню Workbench есть выпадающий список (например, "Limit to 1000 rows") [42]. Некоторые студенты думают, что если там стоит ограничение, то СУБД всегда отдает только это количество строк [42].
*   **Как объяснить на ревью:** Встроенный лимит Workbench ограничивает только отображение в сетке результатов (Result Grid), чтобы не перегружать память ПК [42]. Однако в кодовой базе автотестов или реального бэкенда никакого "Workbench Limit" нет. Если мы не напишем `LIMIT` в самом запросе, бэкенд попытается выкачать миллионы строк, что приведет к Out of Memory. Приучайте писать `LIMIT N` в коде запроса [38]!

#### 3. Проблема: Ошибка синтаксиса при нарушении порядка команд [45]
*   Студенты часто пишут `LIMIT` перед `ORDER BY` или `WHERE` перед `FROM`.
*   **Как объяснить на ревью:** Напомнить мнемоническое правило для запоминания порядка написания ключевых слов: **S**ingle **C**ats **F**ly **T**o **W**est **C**oast (**S**elect, **C**olumn, **F**rom, **T**able, **W**here, **C**ondition) [4]. Строгий порядок: `SELECT` -> `FROM` -> `WHERE` -> `ORDER BY` -> `LIMIT` [45]. Violation = Syntax Error.

#### 4. Проблема: Использование `=` вместо `LIKE` при поиске с маской `%` [4, 58]
*   Запрос вида `WHERE jobTitle = '%VP%'` не возвращает строк.
*   **Как объяснить на ревью:** Оператор `=` ищет точное совпадение со строкой, содержащей символы процентов (буквально ищет текст из 4 символов: процент, V, P, процент). Чтобы использовать шаблоны (wildcards) `%`, необходимо всегда использовать оператор `LIKE` [58].

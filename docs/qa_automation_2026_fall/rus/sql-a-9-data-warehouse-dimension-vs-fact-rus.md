## 🕵️‍♂️ 2. Концепция сессии и QA-контекст тестирования

На 9-м занятии студенты осваивают **проектирование и тестирование аналитических систем хранения данных (DWH)**. В ежедневной практике QA Automation и Manual QA инженера умение работать с DWH позволяет проверять корректность интеграции систем, валидировать отчетность и предотвращать утечки/искажения данных при передаче между сервисами.

### Ключевые QA-цели при изучении DWH, Fact/Dimension и ETL:
1. **Тестирование ETL-конвейеров (ETL Pipeline Testing):** Проверка полноты, точности и корректности трансформации данных при перекачке из транзакционных БД (OLTP) в аналитические таблицы (DWH). Валидация правил очистки (Data Cleansing), обработки `NULL`, генерации суррогатных ключей и отсечения дубликатов.
2. **Валидация бизнес-аналитики и отчетности (BI & Reporting Validation):** Сверка показателей в итоговых отчетах и дэшбордах с первичными фактами. Понимание схем «Звезда» и «Снежинка» позволяет QA строить точные проверочные SQL-запросы для агрегаций (`SUM`, `COUNT`, `AVG`) без лишних тяжелых `JOIN`.
3. **Тестирование снимков во времени (Time Series & Historical Snapshots):** Проверка корректности формирования периодических срезов данных («as of end of month / week») и неизменяемости исторических записей для финансового аудита и регуляторной отчетности.
4. **Валидация витрин данных (Data Marts Testing):** Проверка узкоспециализированных подмножеств DWH, созданных для конкретных отделов (Продажи, Маркетинг, Финансы), контроль соответствия данных между базовым DWH и витринами.
5. **Тестирование суррогатных ключей и производительности (Surrogate Keys & Performance):** Валидация автоинкремента, проверка уникальности ключей и оптимизации индексов в таблицах фактов с миллионами записей.

### 2. Сравнительный анализ: OLTP vs OLAP

| Характеристика | Операционная БД (OLTP) | Хранилище данных DWH (OLAP) |
| :--- | :--- | :--- |
| **Полное наименование** | Online Transaction Processing | Online Analytical Processing |
| **Основная цель** | Регистрация текущих бизнес-транзакций (покупки, платежи, регистрация) | Глубокий анализ бизнеса, трендов, построение отчетности и BI |
| **Модель данных** | Высокая нормализация (3NF) для исключения аномалий | Денормализация (Star / Snowflake Schemas) для ускорения чтения |
| **Ориентация** | Ориентация на приложения (Application-oriented) | Ориентация на предметные области (Subject-oriented) |
| **Атомарность данных** | Детальные оперативные данные в реальном времени (Real-time) | Агрегированные и исторические снимки (Snapshots / Batches) |
| **Тип операций** | Частые, короткие `INSERT`, `UPDATE`, `DELETE`, простые `SELECT` | Массивные `SELECT` с агрегацией (`SUM`, `AVG`, `GROUP BY`), тяжелые пакетные загрузки |
| **Объем и хранение** | ГБ / ТБ в рамках одного сервиса или приложения | ТБ / ПБ, централизованно объединяющие данные всех систем компании |

### 3. Концепция Data Warehouse (DWH) и ETL-процессы
* **Что такое DWH:** Централизованное единое хранилище, собирающее данные из множества независимых источников (продуктовые БД, CRM, ERP, внешние API, CSV-файлы) и приводящее их к единому стандарту.
* **Процесс ETL (Extract, Transform, Load):**
  1. **Extract (Извлечение):** Извлечение сырых данных из операционных источников.
  2. **Transform (Трансформация / Очистка):** Очистка данных (`Data Cleansing`), нормализация имён, обработка пропусков (`NULL`), генерация суррогатных ключей, удаление дубликатов, приведение к стандартам наименований (`t_`, `v_`, `tnp_`).
  3. **Load (Загрузка):** Загрузка подготовленных чистых данных в таблицы DWH.

---

### 4. Таблицы фактов (Fact) vs Таблицы измерений (Dimension)

* **Таблица фактов (Fact Table):**
  * Центральная таблица в архитектуре DWH.
  * Хранит числовые бизнес-метрики (выручка, количество проданного товара, длительность сессии, сумма скидки).
  * Содержит суррогатные внешние ключи (`Foreign Keys`), ссылающиеся на соответствующие таблицы измерений.
  * Характеризуется колоссальным объемом и высокой скоростью роста (миллионы и миллиарды строк).
* **Таблица измерений (Dimension Table):**
  * Содержит текстовые описания, категории и контекст бизнес-событий (информация о клиенте, характеристика товара, гео-локация магазина, календарные даты).
  * Содержит суррогатный первичный ключ (`Primary Key`), передаваемый в таблицу фактов.
  * Меняется сравнительно редко, обладает относительно небольшим числом строк.

### 5. Схемы данных хранилищ: Star Schema, Snowflake Schema, Galaxy Schema

```
        +------------------+
        |  dim_customer    |
        +------------------+
                 |
                 v
+--------------+ +------------------+ +--------------+
|  dim_product |->|    sales_fact    |<-|   dim_store  |
+--------------+ +------------------+ +--------------+
                 ^
                 |
        +------------------+
        |     dim_date     |
        +------------------+
```

1. **Схема «Звезда» (Star Schema):**
   * Центральная таблица фактов непосредственно соединена с денормализованными таблицами измерений.
   * Преимущества: простая и понятная структура, быстрые аналитические запросы, минимальное количество `JOIN`.
2. **Схема «Снежинка» (Snowflake Schema):**
   * Развитие схемы «Звезда», в которой таблицы измерений дополнительно нормализованы на sub-dimensions (например, `dim_dealer` -> `dim_country` -> `dim_region`).
   * Преимущества: экономия дискового пространства, отсутствие дублирования атрибутов измерений. Недостатки: более сложные SQL-запросы с большим числом `JOIN`.
3. **Схема «Галактика» (Galaxy Schema / Fact Constellation):**
   * Содержит несколько таблиц фактов, разделяющих между собой общие таблицы измерений (например, факты продаж и факты остатков на складе разделяют измерения `dim_product` и `dim_date`).

### 6. Снимки во времени (Time Series / Snapshots) и Витрины данных (Data Marts)
* **Time Series & Snapshots:** Фиксация состояния данных на определенный момент времени («as of end of month»). Позволяет строить помесячную и поквартальную аналитику, отслеживать тренды и выявлять фрод.
* **Data Marts (Витрины данных):** Специализированные предметные слои или подмножества DWH, сфокусированные на потребностях конкретной бизнес-группы (например, витрина маркетинга, витрина бухгалтерии). Позволяют предоставлять доступ пользователям без риска повреждения основной базы DWH.

## 🔮 4. Суперсила QA и разбор вопросов студентов с лекции

### ❓ Вопрос 1: «Зачем в таблицах фактов использовать суррогатные целочисленные ID вместо прямого сохранения текстовых имён клиентов или названий товаров?»
* **Ответ ментора:** Таблицы фактов содержат миллионы и миллиарды строк. Повторение длинных текстовых строк (например, "Иван Иванович Иванов" или "Ноутбук Lenovo ThinkPad T14 Gen 3") в каждой строке приведет к гигантскому перерасходу дискового пространства и замедлению операции сканирования таблицы. Использование компактных целочисленных суррогатных ключей (`INT` / `BIGINT`) сохраняет таблицу фактов максимально «легкой», а текстовый контекст хранится в единичном экземпляре в таблицах измерений.

### ❓ Вопрос 2: «В чём принципиальное отличие схем Star и Snowflake с точки зрения QA и составления проверочных автотестов?»
* **Ответ ментора:** В схеме Star измерения денормализованы, поэтому проверочные SQL-запросы пишутся проще, содержат меньше `JOIN` и выполняются быстрее. В схеме Snowflake измерения нормализованы на несколько уровней (например, `Dealer` -> `Country` -> `Region`). При тестировании Snowflake QA-инженер должен тщательно проверять корректность связей между суб-измерениями, отсутствие потерянных внешних ключей и анализировать план выполнения запросов (`EXPLAIN`), чтобы убедиться в использовании индексов.

### ❓ Вопрос 3: «Почему данные в DWH обновляются периодическими пакетами, и как QA проверять снимки во времени (Time Series / Snapshots)?»
* **Ответ ментора:** Обновление DWH производится через пакетные ETL-задачи (ночью, раз в неделю или месяц), чтобы не нагружать боевые OLTP-системы во время активных пользовательских транзакций. QA тестирует снимки данных, фиксируя временной срез (`WHERE snapshot_date = '2026-09-30'`), сверяя агрегированные показатели DWH с первичными транзакциями OLTP и контролируя неизменяемость исторических срезов за прошлые периоды.

### ❓ Вопрос 4: «Как работает AUTO_INCREMENT в таблицах фактов при массовой ETL-загрузке, и что необходимо проверять QA?»
* **Ответ ментора:** При массовой вставке фактов `AUTO_INCREMENT` автоматически присваивает суррогатный первичный ключ каждой новой строке. В ETL-скриптах первичный ключ не передается (или передается `NULL`), а заполняются только `Foreign Keys` измерений и числовые метрики. QA-инженер проверяет отсутствие пропусков и дубликатов ключей, корректность генерации ID при параллельной загрузке нескольких ETL-потоков и последовательность целочисленных значений.

## 💻 5. Практический скрипт: Live Queries & Hands-on Tasks

| № | БД / Объект | SQL Запрос / Операция | Ключевая концепция | 💡 QA-контекст и сценарий проверки |
|---|---|---|---|---|
| **1** | English Dict | `UPDATE dictionary_master SET is_common = 'Yes' WHERE word IN (SELECT word FROM most_common_words);` | Data Cleansing / Enrichment | Обогащение данных и маркировка наиболее частотных слов перед аналитикой. |
| **2** | English Dict | `SELECT is_common, COUNT(*) FROM dictionary_master GROUP BY is_common;` | DQL Aggregation | Проверка распределения частых (4 035) и редких (~107 000) слов. |
| **3** | English Dict | `SELECT word, definition FROM dictionary_master WHERE definition LIKE '%color%';` | Text Pattern Search | Поиск и валидация всех слов, связанных с цветом в определениях. |
| **4** | English Dict | `SELECT word, word_type FROM dictionary_master WHERE is_common = 'Yes' AND word_type IN ('N', 'A') ORDER BY RAND() LIMIT 4;` | Randomization (`RAND()`) | Генерация случайного датасета из 4 существительных и прилагательных для обучения. |
| **5** | English Dict | `(SELECT word, 'Noun' AS type FROM dictionary_master WHERE word_type = 'N' AND is_common = 'Yes' ORDER BY RAND() LIMIT 4) UNION (SELECT word, 'Verb' AS type FROM dictionary_master WHERE word_type = 'V' AND is_common = 'Yes' ORDER BY RAND() LIMIT 4);` | Set Operations (`UNION`) | Комбинирование двух случайных выборок по различным частям речи. |
| **6** | English Dict | `SELECT word, SUBSTRING(word, 1, 1) AS letter1, SUBSTRING(word, 2, 1) AS letter2, SUBSTRING(word, 3, 1) AS letter3 FROM dictionary_master WHERE LENGTH(word) = 7 AND is_common = 'Yes' ORDER BY RAND() LIMIT 1;` | String Processing | Парсинг и посимвольное разбиение слова длиной 7 символов по колонкам. |
| **7** | Family DWH | `CREATE TABLE dim_members (member_id INT AUTO_INCREMENT PRIMARY KEY, member_name VARCHAR(50), gender CHAR(1), birthdate DATE);` | Dimension Table (`dim_`) | Создание таблицы измерений членов семьи. |
| **8** | Family DWH | `CREATE TABLE dim_activity (activity_id INT AUTO_INCREMENT PRIMARY KEY, activity_name VARCHAR(100), description TEXT);` | Dimension Table (`dim_`) | Создание таблицы измерений видов активности. |
| **9** | Family DWH | `CREATE TABLE fact_schedule (schedule_id INT AUTO_INCREMENT PRIMARY KEY, activity_date DATE, member_id INT, activity_id INT, FOREIGN KEY (member_id) REFERENCES dim_members(member_id), FOREIGN KEY (activity_id) REFERENCES dim_activity(activity_id));` | Fact Table & Foreign Keys | Создание таблицы фактов с явным связыванием внешних ключей. |
| **10** | Family DWH | `INSERT INTO fact_schedule (activity_date, member_id, activity_id) VALUES ('2026-10-25', 1, 2), ('2026-10-26', 2, 1);` | Fact Insertion | Внесение фактов расписания с использованием суррогатных ID измерений. |
| **11** | Family DWH | `SELECT m.member_name, a.activity_name, f.activity_date, CASE DAYOFWEEK(f.activity_date) WHEN 1 THEN 'Sunday' WHEN 2 THEN 'Monday' WHEN 3 THEN 'Tuesday' WHEN 4 THEN 'Wednesday' WHEN 5 THEN 'Thursday' WHEN 6 THEN 'Friday' WHEN 7 THEN 'Saturday' END AS day_name FROM fact_schedule f JOIN dim_members m ON f.member_id = m.member_id JOIN dim_activity a ON f.activity_id = a.activity_id;` | DWH Joining & Date Logic | Агрегированный проверочный запрос с декодированием дня недели и объединением фактов с измерениями. |
| **12** | Family DWH | `CREATE INDEX idx_schedule_date ON fact_schedule(activity_date);` | Indexing | Создание индекса по дате факта для ускорения поиска временных срезов. |
| **13** | StarSchemaDB | `CREATE TABLE sales_fact (sales_id INT AUTO_INCREMENT PRIMARY KEY, customer_id INT, product_id INT, store_id INT, date_id INT, quantity INT, total_amount DECIMAL(10,2), FOREIGN KEY (customer_id) REFERENCES dim_customer(customer_id), FOREIGN KEY (product_id) REFERENCES dim_product(product_id), FOREIGN KEY (store_id) REFERENCES dim_store(store_id), FOREIGN KEY (date_id) REFERENCES dim_date(date_id));` | Star Schema Fact Table | Создание центральной таблицы фактов продаж в схеме «Звезда». |
| **14** | StarSchemaDB | `SELECT d.year, p.category, SUM(f.total_amount) AS total_revenue FROM sales_fact f JOIN dim_date d ON f.date_id = d.date_id JOIN dim_product p ON f.product_id = p.product_id GROUP BY d.year, p.category;` | Star Schema Reporting Query | Аналитический запрос выручки по годам и категориям товаров без сложных JOIN. |

| Проблема / Симптом | Корень проблемы | Инструкция ментора по устранению |
| :--- | :--- | :--- |
| **Ошибка: `Cannot add or update a child row: a foreign key constraint fails` при вставке факта** | Вставка записи в таблицу фактов (`fact_schedule` / `sales_fact`) с несуществующим ID измерения. | Объяснить порядок загрузки DWH: сначала заполняются таблицы измерений (`Dimension`), а затем таблицы фактов (`Fact`). |
| **Симптом: Агрегированный отчет «потерял» часть продаж после `JOIN`** | Использование `INNER JOIN` при наличии пустых или несопоставленных ключей измерений в таблице фактов. | Использовать `LEFT JOIN` для выявления сиротских записей и заменять отсутствующие ID техническим значением (например, `-1` = 'Unknown'). |
| **Симптом: Медленное выполнение аналитических запросов по таблице фактов** | Отсутствие индексов на столбцах внешних ключей (`Foreign Keys`) в таблице фактов. | Создать одиночные или составные индексы на столбцы ID (`customer_id`, `product_id`, `date_id`). |
| **Ошибка: Несовпадение финансовых сумм между OLTP БД и DWH за прошлый месяц** | Транзакции в OLTP были отредактированы «задним числом» после снятия снимка данных (`snapshot`) в DWH. | Объяснить концепцию неизменяемости исторических снимков DWH и настроить процесс инкрементальной дозагрузки (CDC - Change Data Capture). |

## 🎯 8. Чек-лист ментора и Definition of Done (DoD)

По итогам ревью-сессии студент должен уметь:

- [-] Объяснить фундаментальные различия между операционными СУБД (OLTP) и хранилищами данных (OLAP / DWH).
- [-] Различать таблицы фактов (`Fact`) и таблицы измерений (`Dimension`), обосновывать применение суррогатных ключей.
- [-] Проектировать схемы данных «Звезда» (Star Schema) и «Снежинка» (Snowflake Schema), понимать их плюсы и компромиссы.
- [-] Составлять аналитические проверочные SQL-запросы, объединяющие таблицы фактов с измерениями.
- [-] Понимать концепцию снимков во времени (`Time Series / Snapshots`) и роль витрин данных (`Data Marts`) в QA-тестировании.
- [-] Применять правила ETL-очистки данных (`Data Cleansing`), обработку дубликатов и корректное связывание внешних ключей.

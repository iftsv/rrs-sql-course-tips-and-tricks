## 🕵️‍♂️ 2. Концепция сессии и QA-контекст тестирования

На 8-м занятии студенты осваивают **управление объектами хранения и архитектурные концепции баз данных**. В ежедневной практике QA Automation и Manual QA инженера выбор правильного типа таблицы или представления критически влияет на скорость прохождения автотестов, стабильность тестового стенда и полноту тестового покрытия.

### Ключевые QA-цели при изучении объектов БД и архитектуры:

1. **Создание Master Views в автотестах и регрессии (`Grand Master Query`):** Построение виртуальных таблиц, объединяющих всю схему данных (`v_classicmodels_detail`, `v_classicmodels_customer`), позволяет автотестам запрашивать любые параметры системы за доли секунды без написания громоздких `JOIN` в каждом тест-кейсе.
2. **Изоляция тестовых данных через `Temp Tables`:** Использование временных таблиц (`tnp_`) для промежуточных расчетов и подготовки тестовых датасетов в рамках одной сессии автотеста без риска загрязнения общей БД или конфликтов с параллельными прогонами.
3. **Валидация транзакционной целостности и отказоустойчивости (ACID):** Понимание атомарности (`Atomicity`) и долговечности (`Durability`) для проектирования негативных тестов бэкенда (эмуляция сетевых сбоев, таймаутов и отката транзакций `ROLLBACK` в финансовых и e-commerce сервисах).
4. **Тестирование распределенных и NoSQL систем (CAP & BASE Model):** Учет задержки синхронизации данных (`Eventual Consistency`) при валидации микросервисов и NoSQL-хранилищ (например, задержка появления черновиков или обновлений профиля).
5. **Профилирование компонентов СУБД:** Анализ работы процессора запросов (`Query Processor`), каталога метаданных и индексов для локализации узких мест и подбора оптимальных таймаутов в автотестах.

### 2. Сравнительный анализ: Table vs View vs Temp Table

| Характеристика | Физическая таблица (`Table`) | Представление (`View`) | Временная таблица (`Temp Table`) |
| :--- | :--- | :--- | :--- |
| **Префикс наименования** | `t_` (например, `t_payments_10k`) | `v_` (например, `v_payments_10k`) | `tnp_` (например, `tnp_payments_10k`) |
| **Хранение данных** | Физически на диске | Не хранит данные (сохраняет только DDL-запрос в метаданных) | Хранится во временной памяти на время сессии |
| **Жизненный цикл** | Постоянно (до вызова `DROP TABLE`) | Постоянно (до вызова `DROP VIEW`) | Автоматически удаляется при разрыве сессии |
| **Видимость в клиенте** | Видна в списке `Tables` | Видна в списке `Views` | Не отображается в боковом меню GUI |
| **Команда создания** | `CREATE TABLE t_name AS SELECT ...;` | `CREATE VIEW v_name AS SELECT ...;` | `CREATE TEMPORARY TABLE tnp_name AS SELECT ...;` |
| **Основной QA Use Case** | Базовые таблицы приложений, стейджинг | Master Views для регрессии, маскирование данных | Промежуточные вычисления во время прогона автотестов |

*💡 Важное замечание ментора:* Команда `DESCRIBE` выполняется абсолютно одинаково для всех трех типов объектов, возвращая их имена колонок, типы данных и ограничения.

### 3. Архитектура СУБД: 5 Ключевых Компонентов

Любая современная СУБД состоит из 5 фундаментальных блоков:

1. **Interface (Интерфейсный уровень):** Язык SQL, сетевые протоколы (TCP/IP) и API-драйверы (JDBC, ODBC) для приема запросов от клиентов и автотестов.
2. **Query Processor (Процессор запросов — "CPU базы данных"):**
   * *Парсинг (Parser):* Проверка синтаксиса SQL.
   * *Валидация (Validator):* Проверка существования таблиц и прав доступа по каталогу метаданных.
   * *Оптимизатор (Execution Planner):* Построение наиболее эффективного плана выполнения с учетом доступных индексов.
   * *Исполнение (Executor):* Чтение/запись данных в хранилище, обновление индексов и метаданных.
3. **Storage (Система хранения):** Физические дисковые блоки или оперативная память (RAM), где лежат страницы данных.
4. **Indexes (Индексы):** Специализированные структуры данных (B-Tree, Hash) для быстрого поиска строк без полного сканирования таблицы (`Full Table Scan`).
5. **Metadata (Метаданные / Системный каталог):** Данные о данных (схемы, имена таблиц, типы столбцов, права доступа, параметры сжатия).

#### Контекст OLTP vs OLAP:
* **OLTP (Online Transaction Processing):** Операционные БД, ориентированные на частые короткие транзакции (INSERT/UPDATE), высокую нормализацию и низкую задержку.
* **OLAP (Online Analytical Processing):** Аналитические хранилища данных (DWH), оптимизированные для сложных агрегирующих запросов по гигантским объёмам данных.

### 4. SQL vs NoSQL, свойства ACID, CAP-теорема, BASE и Vector DBs

#### A. Свойства ACID в SQL-базах данных:
* **Atomicity (Атомарность):** Транзакция выполняется полностью или не выполняется вовсе ("все или ничего"). Сбой на любом шаге вызывает откат (`ROLLBACK`).
* **Consistency (Согласованность):** Транзакция переводит БД из одного корректного состояния в другое, не нарушая ограничений целостности (`Primary/Foreign Keys`, `CHECK`).
* **Isolation (Изолированность):** Параллельно выполняемые транзакции не влияют друг на друга до момента фиксации.
* **Durability (Долговечность):** После выполнения `COMMIT` результаты сохранены на энергонезависимый носитель и не пропадут даже при сбое питания.

#### B. SQL vs NoSQL:
* **SQL:** Высокая структурированность, схема `Schema-on-Write`, поддержка ACID, вертикальное масштабирование (`Vertical Scaling`). Идеально для финансовых и медицинских систем.
* **NoSQL:** Гибкая схема `Schema-on-Read`, высокая производительность чтения/записи, горизонтальное масштабирование (`Horizontal Scaling`). Идеально для социальных сетей, e-commerce каталогов и Big Data.

#### C. Теорема CAP и Модель BASE:
* **CAP Theorem:** В распределенных системах возможно одновременное обеспечение не более **2 из 3** свойств: **Consistency** (согласованность), **Availability** (доступность), **Partition Tolerance** (устойчивость к разделению сети).
* **BASE Model (в NoSQL):** **Basically Available** (базовая доступность), **Soft state** (гибкое состояние), **Eventually Consistent** (согласованность в конечном счете).
  * *Пример из аудио:* Синхронизация черновиков в Gmail. Изменения, внесенные на смартфоне, появляются на ПК через несколько секунд (задержка наступления `Eventual Consistency`).

#### D. Векторные БД (`Vector Databases`):
* Базы данных, специально предназначенные для хранения и поиска данных в виде численных векторов (векторных эмбеддингов). Используются в системах искусственного интеллекта, LLM и семантического поиска.

## 🔮 4. Суперсила QA и разбор вопросов студентов с лекции

### ❓ Вопрос 1: "Зачем создавать Master View на всю БД (`v_classicmodels_detail`), если при соединении всех таблиц возникают дубликаты имён колонок?"
* **Ответ ментора:** Master View создает единую абстракцию данных, избавив QA-инженера от регулярного написания сложного `JOIN`. Однако при объединении таблиц с одинаковыми именами колонок (например, `status` в `orders` и `status` в `payments`) возникают коллизии. В QA-практике при создании View необходимо явно задавать уникальные псевдонимы (алиасы): `SELECT o.status AS order_status, p.status AS payment_status`.

### ❓ Вопрос 2: "Когда в автотестах следует использовать Temp Table, а когда View?"
* **Ответ ментора:** View используется, когда логика или выборка нужна постоянно множеству автотестов или инженеров (например, представление для поиска активных пользователей). Temp Table применяется, когда автотесту нужно временно сохранить промежуточный результат (например, список сгенерированных ID заказов) строго в рамках текущей тестовой сессии, избегая загрязнения основной базы данных.

### ❓ Вопрос 3: "Как проверить свойство Атомарности (Atomicity) при интеграционном тестировании API и БД?"
* **Ответ ментора:** Путем моделирования искусственного сбоя (например, передача некорректного типа данных на 2-м шаге из 3-х в рамках одной транзакции). QA-инженер проверяет, что СУБД автоматически выполнила `ROLLBACK`, и ни одна запись из первого успешного шага не сохранилась в базе.

### ❓ Вопрос 4: "Как правильно автоматизировать проверку систем с задержкой согласованности (Eventual Consistency)?"
* **Ответ ментора:** В NoSQL-базах нельзя выполнять мгновенную проверку (`assert`) сразу после отправки запроса на запись. В QA Automation применяется паттерн ожидания с таймаутом (`Polling / Awaitility`), проверяющий наступление состояния согласованности в течение допустимого SLA-интервала.

| **Ошибка: `Duplicate column name 'status'` при вызове `CREATE VIEW`** | Использование `SELECT *` при объединении таблиц со совпадающими именами колонок. | Явно перечислить колонки в `SELECT` и выдать им уникальные алиасы (`o.status AS order_status`). |
| **Симптом: Временная таблица `tnp_` исчезла или недоступна в соседней вкладке** | Запрос выполнен из другого сетевого подключения. Временные таблицы строго изолированы в рамках своей сессии. | Объяснить студентам концепцию сессионного изолирования и выполнять запросы в той же вкладке. |
| **Ошибка: Изменения DML не видны параллельным автотестам** | В сессии отключен `autocommit`, и не был вызван явный `COMMIT`. | Проверить режим автофиксации через `SELECT @@autocommit;` или выполнить `COMMIT;`. |
| **Падение автотеста NoSQL: `AssertionError` при проверке недавно созданной записи** | Тест пытается прочитать запись с ведомой ноды до завершения асинхронной репликации (`Eventual Consistency`). | Внедрить в автотест механизм повторных опросов (`polling`) с таймаутом ожидания синхронизации. |

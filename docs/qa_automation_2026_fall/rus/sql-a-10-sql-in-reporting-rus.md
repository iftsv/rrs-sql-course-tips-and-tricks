## 🕵️‍♂️ 2. Концепция сессии и контекст QA-тестирования
На 10-й сессии студенты осваивают **роль SQL при тестировании Business Intelligence (BI) и визуализации данных**. В daily-практике QA Automation и Manual QA отчетность BI находится на самом верхнем уровне конвейера данных. Инженер по качеству должен гарантировать, что визуальные виджеты (столбчатые диаграммы, графики, тепловые карты, KPI) точно отражают метрики из underlying SQL-базы данных, а ETL-преобразования не искажают и не теряют данные.

##### Ключевые QA-задачи при изучении SQL в отчетности:
1. **Сверка данных дашборда (Data Reconciliation):** Проверка визуальных значений KPI (общие продажи, средняя продолжительность жизни, общее число инцидентов, количество звонков) путем выполнения прямых проверочных SQL-запросов к таблицам базы данных.
2. **Валидация Master Query и Представлений (Views):** Тестирование единых комплексных мастер-запросов и SQL-представлений, созданных для BI-инструментов (Tableau, Power BI, Looker), на предмет корректности JOIN-логики, обработки NULL и алиасов столбцов.
3. **Тестирование фильтров и параметров:** Проверка того, как BI-фильтры (диапазоны дат, регионы, категории, сотрудники) меняют подлежащие SQL-запросы, и гарантия того, что граничные значения параметров не приводят к дублированию или потере записей.
4. **Тестирование многоисточниковых ETL-конвейеров:** Проверка конвейеров данных, извлекающих сырые записи из гетерогенных систем (софт для записи, телефония, видеозвонки), очищающих и агрегирующих их в MySQL и экспортирующих обработанные таблицы в облачный слой отчетности (Google Drive / Looker Studio).

### 1. Разбор домашнего задания №9 (World DB, Jeopardy DB, Hotel DB)

#### Часть 1: База данных World SQL (`world` DB)
База данных `world` состоит из 3 реляционных таблиц: `city` (4 079 строк), `country` и `countrylanguage`.
* **Подсчет строк и профилирование:** Проверка базового количества записей (`SELECT COUNT(*) FROM city` дает 4 079 строк).
* **Географическая структура:** `SELECT DISTINCT continent, region, name AS country FROM country;` для анализа мирового покрытия.
* **Языковой анализ (Сидней):** Объединение `city` с `countrylanguage` по `countrycode`, где `city.name = 'Sydney'`, для получения списка языков в Сиднее.
* **Формы правления:** `SELECT governmentform, COUNT(*) FROM country GROUP BY governmentform ORDER BY COUNT(*) DESC;` (Республика — самая распространенная форма).
* **Ранжирование по населению:** Ранжирование стран по численности населения по убыванию (`Китай`, `Индия`, `США`, `Индонезия`, `Бразилия`).
* **Разнообразие языков:** Определение стран с наибольшим количеством языков (в ряде стран зафиксировано до 12 языков).
* **Аномалии продолжительности жизни:** Запрос стран с наименьшей продолжительностью жизни (например, Замбия — 37 лет в статических статистических данных).
* **Флаг англоязычных стран (Конструкция `CASE` и подзапрос):**
  * Создание условного флага: `CASE WHEN language = 'English' THEN 1 ELSE 0 END`.
  * Агрегация через `MAX()` или вычисление процента англоговорящего населения для разделения стран на англоязычные и неанглоязычные.
* **Сегментация по населению (< 1 млн vs > 1 млн):**
  * Группировка стран по численности населения (< 1 000 000 и >= 1 000 000).
  * Расчет средней продолжительности жизни с округлением до 2 знаков после запятой с помощью `FORMAT(AVG(lifeexpectancy), 2)`.
  * Результат: 85 стран с населением < 1 млн, 154 страны с населением > 1 млн.
* **Полное объединение базы данных:** Объединение `city`, `country` и `countrylanguage` вместе (дает 4 079 строк на уровне городов).

#### Часть 2: Jeopardy Trivia DB и Hotel Management DB (`hotel_db`)

### 3. Архитектура Master Query (Мастер-запроса) против Database Views для BI

```
+-----------------------------------------------------------------------------------+
|                        РЕЛЯЦИОННАЯ БАЗА ДАННЫХ (OLTP / DWH)                      |
|  +---------------+    +---------------+    +---------------+    +---------------+ |
|  |   customers   |    |    orders     |    | order_details |    |   products    | |
|  +---------------+    +---------------+    +---------------+    +---------------+ |
+----------------------------------------+------------------------------------------+
                                         |
                      [ SQL Master Query / Database View ]
                                         |
                                         v
+-----------------------------------------------------------------------------------+
|                     ДЕНИРОМАЛИЗОВАННЫЙ ПЛОСКИЙ НАБОР ДАННЫХ                       |
| (customer_name, order_date, product_title, category, quantity, total_amount, etc.) |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
|                            BUSINESS INTELLIGENCE (BI)                             |
|                    [ Tableau / Power BI / Google Looker Studio ]                  |
|               (Интерактивные дашборды, фильтрация, визуальные графики)            |
+-----------------------------------------------------------------------------------+
```

#### Зачем создавать Master Query или View для BI?
1. **Разделение логики и визуального слоя:** Сложная логика `JOIN`, форматирование дат и текстовые преобразования выполняются непосредственно на уровне SQL. BI-инструмент подключается к готовой плоской таблице.
2. **Оптимизация производительности:** Снимается нагрузка по тяжелой обработке связей с клиента BI и переносится на сервер базы данных.
3. **Единый источник правды (Single Source of Truth):** Все BI-дашборды и проверочные SQL-запросы QA используют одно и то же протестированное определение (`v_master_reporting`).

### 4. Реальный кейс 1: Аналитика преступности Сан-Франциско и дашборд (SF Crime Data)
* **Характеристика датасета:** Городской полицейский датасет инцидентов с 2018 года по настоящее время.
* **Атрибуты схемы:** ID инцидента, номер инцидента, категория (кража/Larceny, нападение/Assault, мошенничество/Fraud), подкатегория, описание, статус (Resolution), улица / перекресток, полицейский участок, район города, широта, долгота, дата, время, день недели, час (0–23).
* **Аналитические и визуальные паттерны:**
  * **Ранжирование районов:** Сравнение объема преступлений по полицейским участкам и районам (выявление наиболее опасных районов и спокойных жилых зон).
  * **24-часовое распределение:** Пики инцидентов приходятся на **12:00 дня (полдень)** и **12:00 ночи (полночь)**, а наименьшее число преступлений фиксируется в **5:00 утра**.
  * **Преобладающая категория:** Кража / Theft (взлом автомобилей) является самой частой категорией.
  * **Структура дашборда:** Объединение столбчатых диаграмм (по районам), гистограмм (по часам), трендов по месяцам, облаков слов/пузырьковых диаграмм (категории) и географических карт.

### 5. Реальный кейс 2: Многоисточниковый конвейер НКО (HKSpace / Google Looker Studio)
* **Бизнес-контекст:** Некоммерческая организация, предоставляющая эмоциональную поддержку, лайф-коучинг и карьерные консультации по 3 каналам.
* **Разнородные источники данных:**
  1. *CSV софта записи:* Регистрация клиентов и бронирование встреч.
  2. *CSV телефонии:* Журнал входящих и исходящих телефонных звонков.
  3. *CSV видеоконференций:* Записи видеосессий консультаций.
* **Архитектура ETL и отчетности:**
  $$	ext{Сырые CSV-файлы} \longrightarrow 	ext{База данных MySQL (Скрипт очистки и подготовки)} \longrightarrow 	ext{Google Drive / Таблицы} \longrightarrow 	ext{Дашборд Looker Studio}$$
* **QA-наблюдения и юзабилити:**
  * *Учет нагрузки навигаторов/консультантов:* Измерение отработанных часов и объема звонков по каждому сотруднику.
  * *Географическая концентрация:* Пиковые объемы звонков приходятся на **Калифорнию** (базовый регион) и **Флориду**.
  * *Дефекты фильтров дашборда:* Мультиселект-фильтры без кнопки "Сбросить все" создают неудобства для пользователей, пытающихся проанализировать нагрузку одного конкретного навигатора.

## 🔮 4. QA Суперсила и ответы на вопросы студентов с лекции

##### ❓ Вопрос 1: "Почему лучше написать SQL Master Query или View в MySQL перед подключением к Tableau/Power BI, чем перетаскивать отдельные таблицы мышкой в самом BI-инструменте?"
* **Ответ ментора:** Перетаскивание нескольких сырых таблиц внутри BI-инструмента заставляет BI генерировать автоматические и часто неоптимизированные SQL-запросы с избыточными операциями `JOIN`. Написанный вручную SQL Master Query или View гарантирует оптимальные пути объединения, стандартизирует имена колонок, применяет единые `CASE`-преобразования и позволяет QA-инженеру протестировать и провалидировать запрос в MySQL Workbench независимо от визуального слоя.

##### ❓ Вопрос 2: "Как QA-инженер проверяет, что цифры на BI-дашборде (например, в Looker Studio или Tableau) на 100% точны?"
* **Ответ ментора:** QA проводит **сверку данных (Data Reconciliation Testing)**. Для каждого виджета на дашборде (например, "Всего инцидентов за 2024 год = 15 420") QA пишет прямой проверочный SQL-запрос к базе данных с аналогичными критериями фильтрации (`SELECT COUNT(*) FROM sf_crime_data WHERE YEAR(incident_date) = 2024`). Если результат из БД точно совпадает с числом на виджете, виджет считается проверенным. Дополнительно QA обязан протестировать работу фильтров, границы дат и обработку NULL.

##### ❓ Вопрос 3: "В кейсе НКО HKSpace какие потенциальные ETL-баги должен проверить QA при объединении 3 разных источников (запись, телефония, видео)?"
* **Ответ ментора:** Ключевые риски ETL:
  1. *Рассогласование ID / осиротевшие записи:* Клиенты присутствуют в логах звонков, но отсутствуют в базе записи на прием.
  2. *Рассогласование часовых поясов:* Логи телефонии пишутся в UTC, а видеосессии — в местном времени PST.
  3. *Дублирование записей:* Повторный импорт пересекающихся CSV-файлов при пакетных обновлениях приводит к двойному учету звонков или сессий.

##### ❓ Вопрос 4: "Почему статистика преступности SF показывает пики в 12:00 дня и 12:00 ночи, и как SQL-запросы должны обрабатывать аналитику по часам?"
* **Ответ ментора:** Всплески в 12:00 дня и 12:00 ночи обусловлены дефолтными значениями системного времени (когда точное время инцидента неизвестно, системы часто ставят `00:00:00` или `12:00:00`), а также реальной сменой активности в полночь и полдень. В SQL для почасового анализа используется группировка `HOUR(incident_time)` (значения от `0` до `23`, где `0` — полночь). QA должен убедиться, что `0` корректно воспринимается как полночь, а не как пропущенное или NULL-значение.

## 💻 5. Практический скрипт: Живые запросы и задания

| № | БД / Объект | SQL-запрос / Операция | Ключевая концепция | 💡 Контекст QA и сценарий проверки |
| :-: | :--- | :--- | :--- | :--- |
| **1** | World DB | `SELECT city.name, countrylanguage.language FROM city JOIN countrylanguage ON city.countrycode = countrylanguage.countrycode WHERE city.name = 'Sydney';` | Многотабличный `JOIN` | Проверка списка языков для конкретного города через объединенные таблицы. |
| **2** | World DB | `SELECT name, population, CASE WHEN population < 1000000 THEN 'Small (<1M)' ELSE 'Large (>=1M)' END AS pop_category FROM country;` | Условная логика (`CASE`) | Категоризация сущностей по группам для последующей агрегации в BI. |
| **3** | World DB | `SELECT CASE WHEN population < 1000000 THEN 'Small (<1M)' ELSE 'Large (>=1M)' END AS category, COUNT(*) AS country_count, FORMAT(AVG(lifeexpectancy), 2) AS avg_life_expectancy FROM country GROUP BY category;` | Агрегация и `FORMAT()` | Сверка итоговых показателей (<1M: 85 стран; >=1M: 154 страны) для карточек дашборда. |
| **4** | Hotel DB | `SELECT g.first_name, g.last_name, s.service_name, st.transaction_date, st.amount FROM service_transactions st JOIN services s ON st.service_id = s.service_id JOIN reservations r ON st.reservation_id = r.reservation_id JOIN guests g ON r.guest_id = g.guest_id;` | `JOIN` 4 таблиц | Тестирование сложных объединений для проверки отчетов по счетам клиентов. |
| **5** | Reporting / ClassicModels | `CREATE VIEW v_master_reporting AS SELECT o.order_number, o.order_date, c.customer_name, p.product_name, p.product_line, od.quantity_ordered, od.price_each, (od.quantity_ordered * od.price_each) AS line_total FROM orders o JOIN customers c ON o.customer_number = c.customer_number JOIN orderdetails od ON o.order_number = od.order_number JOIN products p ON od.product_code = p.product_code;` | Представление (`CREATE VIEW`) | Создание плоского денормализованного View для бесшовной интеграции с BI-инструментами. |
| **6** | SF Crime DB | `SELECT neighborhood, COUNT(*) AS incident_count FROM sf_crime_data WHERE YEAR(incident_date) = 2024 GROUP BY neighborhood ORDER BY incident_count DESC;` | Агрегация DQL по районам | Сверка столбчатой диаграммы районов на BI-дашборде с данными из SQL. |
| **7** | SF Crime DB | `SELECT HOUR(incident_time) AS incident_hour, COUNT(*) AS total_incidents FROM sf_crime_data GROUP BY incident_hour ORDER BY incident_hour;` | Дискретизация времени (`HOUR()`) | Проверка 24-часовой кривой распределения инцидентов (часы от 0 до 23). |

| **Ошибка: Отсутствуют базы данных (`world`, `hotel_db`) в MySQL Workbench после перезагрузки компьютера.** | Базы данных не были повторно развернуты на локальном экземпляре MySQL. | Поручить студентам найти SQL-скрипты (`world.sql`, `hotel_db.sql`) и выполнить *File -> Open SQL Script -> Execute*, затем *Refresh All*. |
| **Симптом: Итоговые значения на BI-дашборде не совпадают с SQL-запросами `SUM()` или `COUNT()`.** | BI-инструмент применил автоматическое удаление дубликатов, неверные условия фильтрации или отличающиеся диапазоны дат. | Проверить SQL-запрос подключения в BI. Убедиться, что фильтры BI точно повторяют условия секции `WHERE` в проверочных SQL-запросах. |
| **Симптом: Час 0 (полночь) теряется или выводится как неизвестные данные на графиках.** | SQL-запрос использует индексацию от `1` до `24` или некорректно интерпретирует строки `00:00:00`. | Использовать `HOUR(time_column)`, которая возвращает `0` для полуночи. Настроить ось BI для отображения `0` как "Полночь". |
| **Ошибка: Мультиселект-фильтр не позволяет быстро выбрать одного сотрудника без снятия десятков флажков вручную.** | Элемент управления дашборда настроен как чекбокс-список без опции "Одиночный выбор" или поиска. | Обучить QA-тестированию UI/UX фильтров: перенастроить фильтр дашборда на *Single Select Dropdown* или добавить кнопку *Clear Selection*. |

## 🎯 8. Чек-лист ментора и Definition of Done (DoD)
К концу ревью-сессии студенты должны уметь:
* [-] Объяснять роль SQL в архитектуре BI-отчетности и визуализации данных.
* [-] Сравнивать основные BI-инструменты (Tableau, Power BI, Google Looker Studio) и способы подключения к данным.
* [-] Создавать плоский мастер-запрос или представление (`CREATE VIEW`) для передачи очищенных денормализованных данных в отчетность.
* [-] Выполнять SQL-запросы сверки данных (Data Reconciliation) для валидации визуальных виджетов дашбордов.
* [-] Анализировать многоисточниковые ETL-конвейеры (Извлечение -> Обработка в MySQL -> Облачный слой отчетности) и выявлять риски QA.
* [-] Применять конструкции `CASE`, функции времени/даты (`HOUR()`, `FORMAT()`) и многотабличные `JOIN` под комплексные требования отчетности.

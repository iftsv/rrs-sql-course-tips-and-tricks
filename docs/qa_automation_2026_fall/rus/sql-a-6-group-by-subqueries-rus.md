**Ключевые QA-задачи при тестировании GROUP BY, UNION и Subqueries:**
* **Валидация бизнес-метрик и отчётности (KPI & Analytics Testing):** Проверка агрегированных показателей на бэкенде (суммарные чеки, средние чеки, количество активных пользователей по регионам) в сравнении с UI-дашбордами и отчётами.
* **Сверка данных при объединении систем (Multi-Tenant & Data Merging Validation):** Использование `UNION` и `UNION ALL` для проверки миграции данных, формирования рассылок без дубликатов и поиска потерянных записей при слиянии нескольких БД (например, мультибрендовые системы).
* **Фильтрация по агрегированным условиям (HAVING Boundary Testing):** Поиск аномальных клиентов или транзакций (например, клиентов с суммой платежей > $70,000) для тестирования пороговых значений бизнес-логики.
* **Вложенная проверка целостности (Subqueries & CTE for Bug Hunting):** Выделение списков ID через подзапросы для передачи в главный запрос с целью проверки граничных состояний и изолированных выборок.

##### 2. Фундаментальные концепции 6-й лекции

###### A. Первичный профилирующий анализ таблицы (General Data Profiling / Baseline Analysis)
Лектор рекомендует перед глубокой группировкой проводить **полный агрегатный обход** таблицы для построения ментальной карты данных:
* Для текстовых полей: `COUNT(*)`, `COUNT(DISTINCT column)`.
* Для числовых полей: `MIN()`, `MAX()`, `AVG()`, `SUM()`.

*Пример для таблицы `customers`:*
```sql
SELECT 
    COUNT(*) AS total_customers,
    COUNT(DISTINCT country) AS distinct_countries,
    COUNT(DISTINCT city) AS distinct_cities,
    MAX(creditLimit) AS max_credit,
    MIN(creditLimit) AS min_credit,
    AVG(creditLimit) AS avg_credit
FROM customers;
```
*(Результат: 122 клиента, 27 стран, 95 городов, макс. лимит $227,600, мин. $0, средний $67,659)*.

###### B. Группировка данных (`GROUP BY`)
Позволяет применить агрегатные функции к каждой группе отдельно. Правило: колонка, указанная в `SELECT` без агрегатной функции, **обязана** быть продублирована в `GROUP BY`.

*Пример группировки по странам (`customers`):*
```sql
SELECT 
    country, 
    COUNT(*) AS customer_count, 
    COUNT(DISTINCT city) AS distinct_cities, 
    MAX(creditLimit) AS max_credit, 
    AVG(creditLimit) AS avg_credit
FROM customers
GROUP BY country;
```
*(Результат: 27 строк — агрегаты по каждой из 27 стран)*.

###### C. Фильтрация агрегированных результатов (`HAVING` vs `WHERE`)
* `WHERE` фильтрует **исходные строки** *до* того, как выполняется группировка.
* `HAVING` фильтрует **сгруппированные агрегированные значения** *после* того, как выполнена группировка.

*Синтаксический порядок:*
`SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT ...`

###### D. Операции объединения множеств (`UNION` vs `UNION ALL`)
* `UNION ALL`: Объединяет результаты нескольких запросов, **сохраняя все дубликаты**. Работает быстро.
* `UNION`: Объединяет результаты и **удаляет дубликаты** (оставляет только уникальные строки).
* *Требование:* Запросы должны возвращать одинаковое количество колонок с совместимыми типами данных.

*Пример добавления кастомного маркера источника (DB tagging):*
```sql
SELECT city, 'ClassicModels' AS DB FROM customers
UNION ALL
SELECT city, 'MyWork' AS DB FROM department;
```
*(129 строк с `UNION ALL` vs 102 уникальные строки с `UNION`)*.

###### E. Подзапросы (Subqueries) и CTE (`WITH ... AS`)
* **Подзапрос в `WHERE`:** Возвращает список значений (одну колонку) для использования в операторе `IN`.
  ```sql
  SELECT customerNumber, customerName, city 
  FROM customers 
  WHERE customerNumber IN (
      SELECT customerNumber 
      FROM payments 
      GROUP BY customerNumber 
      HAVING SUM(amount) > 70000
  );
  ```
* **Табличные выражения (CTE — Common Table Expressions):** Временный именованный результат, объявляемый через ключевое слово `WITH`. Повышает читаемость и структурированность сложных автотестов и проверок.
  ```sql
  WITH CTE_HighSpenders AS (
      SELECT customerNumber, SUM(amount) AS total_spent
      FROM payments
      GROUP BY customerNumber
      HAVING SUM(amount) > 70000
  )
  SELECT c.customerNumber, c.customerName, c.city, cte.total_spent
  FROM customers c
  JOIN CTE_HighSpenders cte ON c.customerNumber = cte.customerNumber;
  ```

#### 🔮 4. QA Superpower & Вопросы студентов с лекции
Во время лекции 6 возникли важные вопросы. Ментору следует детально разобрать их на ревью-сессии:

##### ❓ Вопрос 1: «Почему мы не можем написать `WHERE SUM(amount) > 70000`?»
* **Объяснение ментора:** Порядок выполнения SQL-запроса следующиий: `FROM` ➔ `WHERE` ➔ `GROUP BY` ➔ `HAVING` ➔ `SELECT`. На этапе `WHERE` строки ещё не сгруппированы, и система не знает сумму по клиенту. Поэтому для агрегатных функций (`SUM`, `COUNT`, `AVG`) используется ключевое слово `HAVING`, которое выполняется *после* группировки.

##### ❓ Вопрос 2: «В чём разница между `UNION` и `UNION ALL` с точки зрения тестировщика?»
* **Объяснение ментора:** 
  * `UNION ALL` сохраняет абсолютно все строки, включая дубли. Если QA проверяет общий объём перенесённых транзакций, `UNION ALL` показывает реальное количество строк.
  * `UNION` выполняет операцию дедупликации. Это полезно при формировании единых списков рассылки или справочников клиентуры, где дубли недопустимы.

##### ❓ Вопрос 3: «Почему `UNION` вернул 102 строки, а `SELECT DISTINCT` по той же выборке — 101 строку?»
* **Объяснение ментора:** `UNION` сравнивает уникальность **всех выбираемых полей** (включая литеральную колонку маркера БД `'ClassicModels'` и `'MyWork'`). Если один и тот же город присутствует в обеих базах, он получит разные метки БД и останется уникальной строкой для `UNION`. При `SELECT DISTINCT` без учета метки БД эти города схлопнутся в 1 строку.

##### ❓ Вопрос 4: «Когда лучше использовать подзапрос (Subquery), а когда CTE (`WITH`)?»
* **Ответ ментора:** Подзапрос удобен для быстрой вложенной фильтрации в одном запросе. CTE рекомендуется использовать, когда запрос содержит несколько этапов трансформации, сложную логику агрегации или повторные соединения — CTE делает тест-скрипт чистым, легко читаемым и поддерживаемым.

#### ⚠ 6. Типичные ошибки студентов и их решение (Troubleshooting Guide)

| Ошибка / Симптом | Корневая причина | Как ментору объяснить решение |
|---|---|---|
| **Error Code: 1111. Invalid use of group function** | Использование агрегатной функции (`SUM`, `COUNT`, `AVG`) внутри секции `WHERE`. | Объяснить, что `WHERE` работает до агрегации. Для фильтрации по агрегатам нужно использовать `HAVING` после `GROUP BY`. |
| **Error Code: 1248. Every derived table must have its own alias** | Вложенный подзапрос в секции `FROM` не имеет присвоенного алиаса (псевдонима). | Показать необходимость всегда добавлять алиас в конце скобок подзапроса: `FROM (SELECT ...) AS sub_table`. |
| **Не совпадают колонки в UNION (`The used SELECT statements have a different number of columns`)** | Разное количество или несовместимые типы колонок в объединяемых запросах `UNION`. | Объяснить правило: каждый `SELECT` в составе `UNION` должен иметь строго одинаковое число и порядок колонок. |
| **Некорректная выдача GROUP BY (лишние или пропущенные строки)** | Выборка колонок в `SELECT`, которые не входят в агрегатные функции и не указаны в `GROUP BY`. | Объяснить правило ANSI SQL: все неагрегированные колонки из `SELECT` должны быть явно указаны в `GROUP BY`. |

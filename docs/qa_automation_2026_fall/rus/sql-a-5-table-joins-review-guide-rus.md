**Ключевые QA-задачи при тестировании JOIN-запросов:**
*   **Сквозная валидация бизнес-цепочек (E2E Integration Testing):** Проверка связей между заказами, клиентами, платежами и товарами (например, корректно ли привязан платеж к клиенту и заказу).
*   **Поиск сиротских записей и битых связей (Orphaned Data & Integrity Checks):** Выявление сущностей без обязательных связей (например, клиентов без назначенного менеджера по продажам или товаров без категории).
*   **Тестирование граничных значений и отсутствующих данных (NULL Testing):** Использование `LEFT JOIN` для обнаружения пропущенных внешних ключей или некорректных NULL-значений.
*   **Раскрытие иерархических структур (Hierarchy Unfolding):** Использование `SELF JOIN` для тестирования ролевых моделей и структур подчинения («сотрудник — руководитель»).

### 2. Фундаментальные типы JOIN

#### A. INNER JOIN (или просто JOIN)
*   **Суть:** Возвращает только те строки, для которых условие соединения (`ON`) истинно в **обеих** таблицах (пересечение множеств).
*   **Синтаксис:**
    ```sql
    SELECT e.empno, e.ename, d.dname
    FROM EMP e
    JOIN dept d ON e.deptno = d.deptno;
    ```
*   **Особенность:** Ключевое слово `INNER` является необязательным и по умолчанию опускается в реальной разработке и автотестах.

#### B. LEFT JOIN (LEFT OUTER JOIN)
*   **Суть:** Таблица, указанная первыми (слева, после `FROM`), является главной. Запрос возвращает **все** строки из левой таблицы. Если в правой таблице нет соответствующего совпадения, колонки правой таблицы заполняются значениями `NULL`.
*   **Синтаксис:**
    ```sql
    SELECT c.customerName, e.firstName, e.lastName
    FROM customers c
    LEFT JOIN employees e ON c.salesRepEmployeeNumber = e.employeeNumber;
    ```
*   **QA Superpower:** Фильтрация по `WHERE right_table.key IS NULL` позволяет находить несвязанные сущности и баги целостности данных.

#### C. SELF JOIN (Соединение таблицы с самой собой)
*   **Суть:** Таблица соединяется сама с собой через использование двух разных псевдонимов (алиасов). Применяется для раскрытия иерархических связей внутри одной таблицы.
*   **Синтаксис:**
    ```sql
    SELECT 
        e.employeeNumber AS emp_id,
        CONCAT(e.firstName, ' ', e.lastName) AS employee_name,
        CONCAT(m.firstName, ' ', m.lastName) AS manager_name
    FROM employees e
    LEFT JOIN employees m ON e.reportsTo = m.employeeNumber;
    ```
*   **Назначение:** Поднимает иерархическую связь «сотрудник — менеджер» на один уровень (в одну строку) для удобной проверки.

#### D. FULL JOIN и CROSS JOIN
*   **FULL OUTER JOIN:** Возвращает все записи из обеих таблиц, заполняя `NULL` несовпадения с обеих сторон (в MySQL эмулируется через `UNION` из `LEFT JOIN` и `RIGHT JOIN`). В ежедневной QA-практике используется крайне редко.
*   **CROSS JOIN:** Декартово произведение (каждая строка первой таблицы с каждой строкой второй). Используется преимущественно для генерации комбинаторных тестовых наборов данных.

## 🔮 4. QA Superpower & Вопросы студентов с лекции

Во время теории лекции 5 студенты задавали практические вопросы. Ментору следует повторно разобрать их на ревью-сессии:

### ❓ Вопрос 1: «Почему при INNER JOIN получилось 100 записей, хотя в таблице customers 122 записи?»
*   **Контекст:** При соединении `customers` (122 строки) и `employees` (23 строки) по ключу `salesRepEmployeeNumber` через `INNER JOIN` выдача составила 100 строк.
*   **Объяснение ментора:** `INNER JOIN` отсекает все записи, где условие соединения не выполняется. У 22 клиентов поле `salesRepEmployeeNumber` содержит `NULL` (менеджер не назначен).
*   **Как проверить:** Запустить `LEFT JOIN` с фильтром `WHERE e.employeeNumber IS NULL`. Запрос выведет ровно 22 клиентов.

### ❓ Вопрос 2: «Могут ли записи выпасть из INNER JOIN не из-за NULL, а по другой причине?»
*   **Объяснение ментора:** Да! Если в левой таблице указан ID (например, `salesRepEmployeeNumber = 1800`), но в таблице `employees` сотрудника с таким `employeeNumber` не существует (битая ссылка / битый внешнее ключ).
*   **QA-вывод:** `INNER JOIN` скрывает такие записи, а `LEFT JOIN` подсвечивает их (показывает `1800` слева и `NULL` в полях менеджера справа), что является критическим багом целостности данных.

### ❓ Вопрос 3: «Какую таблицу ставить первой (слева) при LEFT JOIN?»
*   **Ответ ментора:** Первой (слева) всегда ставится **главная исследуемая таблица**, сохранность всех записей которой мы хотим гарантировать (например, таблица клиентов, заказов или пользователей).

### ❓ Вопрос 4: «Зачем нужен SELF JOIN, если все данные и так лежат в одной таблице?»
*   **Ответ ментора:** Таблица `employees` хранит только ID руководителя (`reportsTo = 1002`). Чтобы узнать имя и фамилию руководителя в том же запросе, мы соединяем таблицу `employees` с собой же, проецируя `reportsTo` на `employeeNumber` второй копии таблицы.

## ⚠️ 6. Типичные ошибки студентов и их решение (Troubleshooting Guide)

| Ошибка / Симптом | Корневая причина | Как ментору объяснить решение |
|---|---|---|
| **Error Code: 1052. Column '...' in field list is ambiguous** | Выборка колонки (например, `employeeNumber`), которая присутствует в обеих объединяемых таблицах, без указания алиаса. | Объяснить необходимость явной квалификации колонок через алиасы: `c.customerNumber` или `e.employeeNumber`. |
| **Пропали данные при объединении таблицы клиентов и менеджеров** | Использование `INNER JOIN` вместо `LEFT JOIN` при наличии NULL в ключах связывания. | Показать разницу между строгой фильтрацией (`INNER`) и полным сохранением левой таблицы (`LEFT`). |
| **Перепутаны местами таблицы в LEFT JOIN** | Поставлена второстепенная таблица на первое место после `FROM`. | Научить правилу: левая таблица — это главная сущность, записи которой **нельзя терять ни при каких обстоятельствах**. |
| **Путаница условий ON и WHERE** | Фильтрация бизнес-условий записана внутрь секции `ON` вместо `WHERE`. | Объяснить разделение ответственности: `ON` задает правило связывания таблиц, а `WHERE` фильтрует итоговый результат. |
